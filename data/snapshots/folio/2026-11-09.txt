 Why Folio
 We replaced Confluence with it. This is what we wanted from a wiki.
 You own the content.
 Every page is a plain file in a Git repository you control. No export step, no lock-in: stop using Folio tomorrow and the files are still there, readable in any editor.
 It works the way a wiki should.
 Real-time editing, a page tree, search, access rights, history, sharing. It keeps working offline.
 Agents are first-class users.
 Not a chatbot bolted on the side: a built-in assistant, your own agent in every space, a full MCP server, and Markdown links made for agents.
 One tree for everything.
 Documents, tables, whiteboards, diagrams and files side by side. A roadmap table next to the spec, next to the architecture board, next to the signed PDF.
 One command to run.
 Docker, and nothing to configure for a first start.
 Access you can read at a glance.
 Roles per space, rights per page that child pages inherit, groups, an access matrix and an audit log with CSV export. The instance administrator is not automatically a reader of private spaces.
 A look at a new hire&#x27;s first week: the rep asks Folio AI and gets answers from the team&#x27;s own wiki, with sources. A short weekly check is a Folio form, and the manager reads the answers in a table. 
 Git-first, all the way down
 Most wikis keep your content in a database and offer Git as an export. Folio does the opposite: the Git repository is the wiki. The database holds the index, access rights and the state of live editing, never the only copy of your words.

 Edit anywhere. Change a page in the browser or in your IDE and push. Both land in the same history. Links between pages are ordinary relative Markdown links, not a private dialect. 
 Bring your own repository. Start with an empty space, clone an existing repository, or connect one later. Several spaces can share one repository, each in its own folder, so documentation can live right next to the code. A space bound to a folder such as docs/ writes no ids into your files and keeps the front matter keys of Docusaurus, MkDocs, Hugo or Jekyll as they are. 
 Review like code. Merge requests, blame, diff and revert work on your wiki because it is a repository. 
 Nothing is lost quietly. Sync state is always visible: clean, ahead, behind, conflict. Conflicts are listed for the whole space. “Take the version from Git” resets a space to the remote branch and saves what was there into a backup branch first. 
 Honest detail: the commit is made after about 90 seconds of quiet, or right away with the Sync action. Right after saving, the history may still be empty.

 What you get today
 Everything below works in the code today. What does not exist yet is in the Limitations section further down.
 Write together
 Documents, data tables and whiteboards are edited by several people at once. You see who is on the page and where their cursor is; changes appear as they are typed. When the page goes quiet, Folio commits, with the person who edited as the author.

 Documents
 A Markdown editor that does not make you think about Markdown. Three modes: Reading, Live edit and Source.
 Callouts, checklists, tables with merged cells and colors, code blocks, collapsible sections, highlights.
 Paste from Excel and Google Docs keeps tables and formatting.
 [[ links a page, @ mentions a person, / inserts anything.
 Outline, backlinks, page icons and covers, glossary terms with hover cards.
 Your own page templates: save any page, board, table, form or page with subpages as a template, and pick it from the "+" menu. A new space starts with Meeting notes, How-to and Decision record.
 Light and dark themes, following the system or chosen by hand.

 Diagrams you draw, not type
 Mermaid diagrams come with a visual editor. You build the diagram on a canvas and Folio writes the Mermaid code, or you type the code and the canvas follows.
 Nine diagram types from templates: flowchart, sequence, classes, states, ER, Gantt, timeline, pie, mind map.
 Code and canvas side by side, full screen when you need room.
 Still plain Markdown: the diagram is stored as an ordinary mermaid code block, so GitHub and GitLab render it too.
 A visual Mermaid editor: code on the left, the diagram on the right 
 Data tables and forms
 Spreadsheets that belong to the wiki: typed columns, saved views, filters and sorting. A small database you can link from any page and query from any agent.
 Column types: text, long text, number, date, checkbox, select, status, user, link.
 Views as tabs, each with its own columns, order, widths, multi-column sort and and/or filters, including me, today, this week.
 Edited together in real time, stored as one readable file in Git.
 Import and export; up to 20,000 rows per table.
 Forms turn a table into a questionnaire: every answer becomes a row. A form can be public, so people answer without an account.

 Whiteboards
 Excalidraw boards inside the wiki: architecture, flows, workshops. Drawn together in real time and saved as SVG files that render anywhere. The board in the screenshot was created by an agent over MCP from a short description of boxes and arrows; people then keep editing it like any other board.

 Files are pages too
 PDF, Word, Excel and PowerPoint files open right inside Folio: no download, no other application, no conversion on the server. The file sits in the space&#x27;s Git repository next to the pages about it, under the same access rights. Folio never rewrites your file.
 View only. These files are not edited in Folio, and search finds them by title.

 Artifacts from your AI agents
 The dashboard, calculator or checklist that Claude or Cursor built no longer stays in one chat. Tell the agent "publish this dashboard to Folio, in Reports" and it becomes a page of your wiki: in the tree, in search and in Git, under the same access rights as everything else.
 Interactive, not a screenshot: filters, tabs and charts work on the page, and each reader&#x27;s choices survive a reload.
 Agents publish over MCP with publish_artifact; people can paste HTML or upload an .html, .zip, .svg or .md file.
 Stored as a <name>.artifact/ folder in the space&#x27;s repository: the page, an artifact.yaml manifest, the original source and assets.
 Runs in a sandboxed frame with no access to your Folio session or API.
 Folio shows the finished page and does not build React itself, so the agent sends HTML that already runs. Calls to Claude or your own APIs do not work inside an artifact, and claude.ai share links are not downloaded.
 A Claude artifact published to Folio: a sales dashboard with live filters, as a page of the wiki 
 Works offline
 On a train, on a plane, on bad hotel Wi-Fi: keep writing. Pages and whiteboards you have opened stay editable without a connection. New pages and whiteboards can be created offline. Everything is kept on the device and reaches the server by itself when the connection returns, at the same address, with no duplicates. An indicator in the header shows what is waiting to be sent.
 Data tables, forms and file uploads need a connection.
 Writing a new page with no connection; it syncs when the network is back 
 Access management
 Who sees what is decided in one place, and it is visible at a glance.
 Roles per space: administrator, editor, viewer.
 Private, open to everyone signed in, or public, and rights per page that can be narrower than the space. A restriction on a page is inherited by its child pages; a child can narrow it further, not widen it.
 Groups hold space roles and page grants. Make them by hand, or let them follow your identity provider: groups synced at sign-in or through SCIM. Groups cannot be nested.
 The access matrix: people down the side, spaces across the top, a role in every cell.
 An administrator is not a reader: the instance administrator does not see the content of private spaces they are not a member of. They can grant access to themselves, and that is written to the audit log and marked for everyone to see.
 Invitations by link with a role, an expiry date and a usage limit; access requests.
 Sign-in: email and password, Google, any OpenID Connect provider (Keycloak, Authentik, Entra ID, Okta) and SAML 2.0 (Entra ID, Okta, Keycloak, Google Workspace, ADFS). SSO can be enforced per email domain, with an audited admin break-glass, and SCIM 2.0 provisions users and groups (Okta, Entra ID).
 An audit log screen with CSV export. Session management: sign out your other devices. Deactivating a person revokes their sessions, API tokens and MCP connections.
 Share links for people without an account: view or edit, one page or a whole subtree, revocable at any time.
 A whole space can also be published as a public website (see the use cases below).
 SSO, SCIM, groups and the audit log are in the one MIT edition. There is no paid tier.

 What teams do with it
 Two setups that need no extra service: one Folio, one Git repository.
 Publish a space as a public website
 Set who can read a space to public and Folio serves it as a read-only website: the page tree, search inside the space, documents, live data tables, whiteboards as pictures, PDF and Office files. The site is the space itself, so there is no second copy to keep in step.
 Three addresses: a path on your Folio, a subdomain, or your own domain such as docs.example.com.
 Visitors can download a page as Markdown, PDF or DOCX if you allow it, and ask Folio AI about the space if you switch that on.
 A page with its own restrictions is never published, and nothing is copied: the site is the space.
 Honest limits: the subdomain and the domain need DNS, a certificate and proxy rules on your side. A page with a restriction is never published, and its child pages inherit the restriction, so they stay closed too.

 Docs as code, edited in a browser
 The docs/ folder of your product repository becomes a space. A technical writer edits the pages in the browser. The developer sees an ordinary commit with the writer&#x27;s name as the author. An agent connected over MCP with the developer&#x27;s token updates the same pages, with that developer&#x27;s rights and no more. The space can then be published as the documentation portal.
 Your files stay as they are: no ids written into them, and front matter from Docusaurus, MkDocs, Hugo or Jekyll is kept.
 Moving or renaming a page rewrites the links to it in the same commit; pasted images can go to the repository.
 Review, branch and revert with the Git tools you already use.
 Honest limits: the commit is made after about 90 seconds of quiet, and only [text](path) links and images are rewritten.

 Made by agents. Built for agents.
 The owner chose what to build and checked every flow. Agents wrote the code, tests and docs. Now agents work with the same pages as people.
 Folio AI
 An assistant in the side panel that works with your wiki, not next to it. Ask is read-only: find, summarize, compare, explain across the pages you have access to. Agent reads and writes: drafts a page, updates a table, draws a board, restructures a section, inside your rights and never beyond them. It runs on the server, so closing the browser does not stop the work. It uses the very same tools an outside agent gets over MCP, and in Ask mode the write tools are switched off on the server, not just hidden.
 The built-in assistant adds a table row and answers from the data Bring your own subscription

 .agent: your own agent in every space
 Every space has a .agent folder. Whatever you put there becomes the assistant&#x27;s instructions for that space, written as ordinary Folio pages, not as configuration.
 Build an agent by writing pages: its role, tone, glossary, rules, templates and process.
 A different agent for every team: the support space gets an agent that answers like support, engineering gets one that knows the release process.
 Versioned like everything else: you can see who changed the agent&#x27;s behavior, review the change, and roll it back.
 Owned by administrators: only space administrators see and edit .agent.
 One agent per space.
 MCP server
 49 tools over /mcp, with a personal access token or OAuth: list and search spaces, read and write pages, create and edit whiteboards, forms, data tables and bases, read the link graph and history, and check a page against the space&#x27;s writing rules.

 Run it
 You need Docker and Git. Nothing else.

 git clone https://github.com/evergreen-it-dev/folio.git
cd folio

 The first start builds the application and takes a few minutes (about 1 GB is downloaded). Then open http://localhost:4870 and create the first account. It becomes the administrator.
 A short welcome takes it from there: pick what to create first (a document, a whiteboard or a data table), look through what Folio can do, and land in your first space with that page open. Connecting an existing Git repository is one link away on the same screen.

 Limitations, said plainly
 Deliberate limits and known gaps, so you do not spend time looking for what is not there.
 PostgreSQL and Redis are required. Page content lives in Git, but the index, access rights and live-editing state live in PostgreSQL.
 No serverless hosting. Folio needs a long-running process, a persistent disk and WebSocket connections.
 Groups cannot be nested. A group holds space roles and page grants; a group inside a group is not supported.
 No end-to-end encryption of content, and no LDAP. The server holds the content. Sign-in is email and password, OpenID Connect or SAML 2.0.
 The built-in assistant needs a Cursor subscription. Other providers are not supported yet.
 The public demo is shared and resets daily. One login for everyone, data reset every 24 hours; tokens, Git and import, share links, invitations and the AI assistant are off. The Folio Handbook is published there as a website (its administrator can try "Publish as website"). Do not enter personal data or API keys.
 One agent per space. 
 File names are Latin only. A page title in any script is fine; the file name cannot be.
 Readers see a whiteboard as a static picture. 
 PDF and Office files are view-only and searchable by title, not by content.
 A child page can narrow an inherited restriction, not widen it. 
 Moving a page rewrites only [text](path) links and images. HTML tags and reference-style links are left as they are.
 A public site is read-only and anonymous. No comments, history or form submissions. Each site gets its own robots.txt and sitemap, and a switch keeps search engines out.
 Search has no stemming. Different forms of a word are different words.
 A remote repository can be connected only if it is empty. To start from an existing repository, create the space by cloning it.
 Confluence import does not support every macro. Run a test import before moving a whole space.
 Offline mode covers documents and whiteboards opened on the device before. Tables, forms, uploads and templates need a connection.
 No separate mobile or desktop app. The interface is responsive in the browser.
