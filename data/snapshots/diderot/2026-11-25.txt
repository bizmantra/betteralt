 Ask what your team's coding agents did, and why.
 A coding agent's session holds what nothing else records: the commands it ran, what they printed, what it tried and abandoned, and why. Diderot is an open-source server you run. It indexes those sessions alongside your team's chat, issues and docs, searches all of it over several rounds, and answers with citations.

 Memory an agent searches, instead of a file it loads
 A memory file such as CLAUDE.md or AGENTS.md is loaded into the context window at the start of every session, whether the task needs it or not. Someone has to keep it short enough to fit, and it lives in one repository or on one machine.
 Diderot keeps agent sessions alongside your team's chat, issues and docs in Postgres and Qdrant. Corpus text enters an agent's context window only when the agent calls a tool: retrieve for the passages that match a question, expand for up to 64 KiB of the transcript, thread, issue or page behind a hit. A new session can find what an earlier one did, yours or a colleague's, within what the caller may read.

 $ 
diderot ask "In the app repo, why are lexicons:install ('lex install') and lexicons:verify ('lex install --ci') separate scripts, with verification in an explicit CI step instead of postinstall? Find the implementing PR or discussion."
 Because the app commits its lexicons, so there is nothing to fetch at install time. Install-time work is pure codegen, and lex install --ci is only a drift check on files already in git, which belongs in the PR gate. package.json
, lint.yml
 The first draft followed the upstream README literally and chained lex install --ci && lex build into postinstall. Priya's Claude session
 By the version reviewed and landed, three weeks later, verify had moved out to a lexicons:verify entry in the lint matrix. Priya's later Claude session
 The same reviews spell out the cost of loading postinstall: it runs on every install without --ignore-scripts , including the Docker image build, so a broken vendored lexicon would fail pnpm install outright. That's tolerable for lex build (deterministic, offline, needed for the tree to compile) and not for a network-resolving verification. I didn't find a written-up design doc; the rationale I can cite lives in the PR reviews.

 Several rounds of retrieval, not one search
 Diderot's first move is one search across every source. Each source is ranked on its own and the best few results of each come back together, so a runbook or an issue is not buried under a busy chat. Then it works in rounds: retrieve in one source for more, list for everything matching a filter, expand for the full thread, page, issue or stretch of a session around a hit. It answers when every claim rests on something it has read, and cites it.
 If you connect them, it can also search your code, search the web, call the read-only tools of MCP servers you connect in the admin UI, and hand an investigation of your telemetry to a separate investigator. Slack, Discord, the shell, MCP and the HTTP API all run this same loop.

 The answer to a real question is usually spread across chat, the tracker, the wiki and agent sessions. Instead of asking a Slack assistant, then a Linear one, then grepping transcripts, you ask one corpus that holds all of it.

 Slack Messages and threads in the channels the bot is in, with their images and PDF, DOCX and XLSX attachments. 
 Discord The channels you choose, with their threads and forum posts.

 Zendesk Tickets, their comments and Help Center articles.

 Images too. AI vision reads what is inside your images, so screenshots, charts and scanned documents are searchable by their content.
 Your models, your prompts
 See Inference providers
 and Prompts
.
 Every job takes the model you give it
 Diderot ships with no model and starts with none configured. In the admin UI you add a provider: OpenAI, Anthropic, or anything that speaks OpenAI's API, such as a gateway or a local Ollama or vLLM. Diderot lists the provider's models, and you choose one for each job: answering, embedding, summarizing sessions, describing images. Each is tested before it is saved, and there is no configuration file for any of it. One install can mix a hosted model for answers with a local one for embeddings.
 Every prompt is yours to change
 The instructions Diderot sends to a model are named prompts in one catalog: how Ask researches, how it writes for Slack, how it summarizes a session, describes an image and investigates an alert. You edit them in the browser. Changes collect in a draft, shown line by line against the live text, and go live together as one version with a note. Any earlier version can be made live again, and an optional note about your organization tells Ask where your team keeps things.

 For coding agents
 See The diderot command
 and MCP endpoint
.
 To connect your coding agents, install the diderot client on your own machine and give it a server's URL. It signs in, registers Diderot's MCP server with the coding agents you name, and installs the skill that teaches them when and how to use it:
 brew install bluesky-social/tap/diderot
 diderot setup https://diderot.example.com \
 --harness claude-code,codex
 diderot doctor
 diderot ask "What did we decide about the billing migration?"
 setup Knows Claude Code, Codex, Cursor, OpenCode and Pi. It works out how to sign in from the URL: an API token, or OAuth in your browser when the server or a gateway in front of it publishes MCP authorization metadata, as a Diderot server in oidc mode does. It changes only the diderot entry in each agent's configuration, and running it again is safe. 
 doctor Checks the connection, the sign-in and everything setup configured. It changes nothing. 
 ask Asks from the shell and prints the answer with its citations. --session asks a follow-up in the same conversation. 
 sessions On a terminal, after sign-in, setup checks that the server takes sessions from your account, lists the Claude Code and Codex session directories it finds on your machine, and offers to ship them. If the server does not, it asks nothing and installs nothing. Yes installs a background service under your own account, a launchd agent on macOS or a systemd user unit on Linux. It converts each session on your machine and sends the whole transcript to that server, unredacted, with images left out. diderot sessions install does the same later, and uninstall removes the service. Sessions are stored but not searchable until an administrator has chosen a model for both session-summary jobs on the server's Models page. 
 Without Homebrew, download the release archive
 for Linux or macOS and check it against the release's checksums.txt , or build it with go install github.com/bluesky-social/diderot@latest . The download holds only the client commands setup , doctor , ask and sessions ; the server's commands are in the container image. Off a terminal every command prints one JSON object, so scripts and agents can drive it.
 The MCP server underneath
 Everything setup , doctor and ask do goes through the server's MCP endpoint, /mcp , which every install serves over streamable HTTP with the same bearer token the HTTP API takes. Any other MCP client can point at it directly. It has the tools Ask itself uses, retrieve , list and expand , plus attachment , which returns an image or a document's extracted text, and ask , which returns a full cited answer. ask runs as an MCP task, so it needs a client that implements the MCP Tasks extension; the other four work in any client. Each call sees what the caller's identity may see.
 Without MCP, the same token works on the plain HTTP API: POST /v1/ask , /v1/retrieve , /v1/list and /v1/expand-chunk .

 How it is built
 See Design
 and Adding a source
.
 Connectors read each source, by live events, periodic sync, HTTP push or a folder scan, depending on the source.
 The events sink writes one row per message, page, issue or session, idempotent on source and external ID. It skips content that has not changed, so nothing is embedded twice.
 Postgres is the source of truth: events, chunks, settings, prompts and every Ask conversation.
 The embedder cuts each event into chunks, embeds them through your embedding model, and marks a chunk embedded only after its vector is written. A vision model describes each image and transcribes its text; the embedder embeds that description, not the pixels.
 Qdrant holds the vectors, with each chunk's permission scope in its payload.
 Surfaces : a mention or direct message in Slack or Discord, the MCP server at /mcp , and POST /v1/ask . All run the same loop.
 Ask calls retrieve , list and expand , plus any optional tools you enabled, until it can answer. retrieve searches Qdrant; list , expand and the text of every hit come from Postgres, which checks each event's scope a second time.
 Model providers are the endpoints you add in the admin UI, called by the embedder and by Ask. Each request goes to the provider its model names, with that provider's key.
 Retrieval is vector-only: Diderot embeds the question and Qdrant returns the nearest chunks the caller may see. A search across several sources ranks each source on its own and returns the best few of each. There is no reranker and no keyword index. When a question contains an exact handle (a Slack permalink, a Linear issue key, a session ID), Diderot reads that record directly instead of searching.
 A source of your own is one Go package and one registration line.
 Running it for a team
 See Running in production
, with a complete Kubernetes example, and the configuration reference
.
 The server One image runs the HTTP API, the browser UI, the MCP endpoint and the background workers. It is distroless, runs as a non-root user, and comes for linux/amd64 and linux/arm64 . Each release is published at ghcr.io/bluesky-social/diderot ; to run a change of your own, build it with the repository's Dockerfile . 
 Postgres 14 or later Holds every event, setting, sealed secret and conversation. The server applies its own migrations when it starts. Connect directly or through a session-mode pooler. 
 Qdrant Holds the vectors, over gRPC, with optional TLS and an API key. It needs no backup: Postgres can rebuild it, at the cost of embedding the whole corpus again, and searches find less until that finishes. 
 Model providers At least an embedding model and a model for Ask, added on the Models page once the server is up. Each request goes to the provider its model names, with that provider's key and no other. 
 Object storage, optionally An S3-compatible bucket, if you want image captions and PDF, DOCX and XLSX extraction. Without one, attachments are not indexed. 
 An identity provider, or not OIDC bearer tokens from your IdP, static tokens, or a loopback-only mode with no auth. The browser UI signs in through your IdP, sits behind an authenticating proxy, or signs in locally.

 A job runs only if some provider you added speaks its protocol; there is no fallback between providers. So with only Anthropic, conversations have no titles, and embeddings need a second provider, such as a local embedding server.
 Replicas
 Every replica serves the UI, retrieval, and Ask over the API and MCP. Work that must run once per deployment runs on an elected leader, chosen by a Kubernetes Lease or a Postgres advisory lock: the Slack connection and its answers, the embedder, and every connector's sync. More replicas add a standby for that work, not capacity for it.
 The server exposes health and readiness endpoints, and Prometheus metrics on a port of their own. During a rolling update, the old release runs against the new schema. The project does not guarantee that this works.

 Who can read what
 Diderot stamps every event with one scope when it ingests it. Every search filters on the caller's scopes, in the vector query and again when the text is read from Postgres. The server computes those scopes from where the question was asked; the model never chooses them.

 What leaves, and where to
 Model providers. Each Ask question, with the conversation so far and the corpus text its searches returned, private Slack messages included. A short title for each new conversation. Text to embed, unless the embedding model is local. Session transcripts, images, PDF pages and Slack threads, when you turn on summaries, captions, extraction and thread summaries.
 The services you connect. The APIs of the connectors you enable; Tavily, if you turn on web search; your Sourcebot, for code search; and the servers of your tool connections.
 Your own infrastructure. Postgres, Qdrant, your object storage and your identity provider, wherever you run them. The quickstart's one other outbound connection is the first-start download of its embedding model from Hugging Face.
 What it does
 Keeps credentials separate. The API and MCP share one bearer credential. A browser credential is never accepted on either, and an API or MCP credential is never a browser session.
 Seals pasted secrets. Diderot encrypts connector secrets entered in the admin UI with AES-256-GCM under a key you hold, or reads them from environment variables.
 Audits administrators. Each state-changing action in the admin UI is recorded with the actor's email, its target and its outcome.
 Admits Ask's MCP tools read-only. An administrator ticks the tools Ask may call on each tool connection. A ticked tool attaches only if it is in a reviewed read-only set or the server marks it read-only, unless the connection explicitly allows otherwise.
 Hides events with no scope. If Diderot cannot determine an event's scope, no one can read it until it is stamped.
 What it does not do
 Mirror source permissions. Access rules inside Notion and Linear are not carried over: every signed-in user can read what you index from them, and Linear's private teams are not indexed. For people asking outside Discord, Discord's roles are not copied either: you choose who may read each channel when you index it. Every signed-in user can also read an agent session unless its owner marks it owner-only.
 Redact. Neither the server nor the diderot client redacts a session: the client converts it and sends the whole transcript, images left out, and the server stores, summarizes, embeds and shows what arrives. Strip secrets before a session is sent, or leave a directory out with diderot sessions install --exclude .
 Hide conversations from administrators. An administrator can read every Ask conversation in the admin UI.
 Terminate TLS. Every listener speaks plain HTTP, and the metrics port has no authentication.
 Rerank or match keywords. Retrieval is vector-only.
 Know who a Discord user is. Discord gives a bot no email, so a question asked in Discord draws only on public content and the Discord channels its audience can read.
 Serve more than one Slack workspace. 
 Match a person whose email differs between your IdP and Slack. Email is the identity key.
 Ship a Helm chart. You adapt the Kubernetes example.
 Undo a migration, or delete one source's data on request.
 To report a vulnerability, email security@bsky.app rather than opening a public issue.
 Questions
 Can I use it without Slack? Yes. Each source is turned on separately, the setup checklist needs only one, and the MCP server and HTTP API are on every install. So a deployment can index Notion, Linear, a folder of Markdown files or agent sessions and answer over MCP alone. Scheduled reports and PagerDuty investigations are delivered through Slack, and wait while it is off.
 How do agent sessions get in? The diderot client sends them, or an uploader of your own does. On a terminal, after sign-in, diderot setup checks that the server takes sessions from your account, lists the Claude Code and Codex session directories on your machine, and offers to ship them. Yes installs a background service that converts each session there and sends the whole transcript to your server, with images left out and nothing redacted. A Diderot you run for yourself needs no other collector. An uploader of your own can push session files to the HTTP endpoint instead, in the format the agent writes: Claude Code, Codex, ATIF or Hugging Face session traces. Either way the server needs session push turned on, and sessions are stored but not searchable until an administrator has chosen a model for both session-summary jobs on the Models page, one that passes each job's test. Everyone who can sign in can read a session unless its owner chooses Only me for it on their sessions page. See The diderot command
 and Agent-session ingest
.
 Does Slack need to reach my server? No. Diderot connects out to Slack over Socket Mode, so the server needs no public URL. The one inbound webhook is PagerDuty's, on a port of its own. That listener is always open, and answers 404 unless you turn PagerDuty investigations on.
 What happens to questions asked while it is down? Messages sent while Diderot is down are read when it comes back, by the sync that backs up live events. A mention is answered only if Slack delivers it again: with Slack's Delayed Events setting on, questions asked during a short outage are answered too. See Keeping it running
.
 What will it spend on model calls? Each Ask question is one model call per round of searching and reading, up to a limit you set (8 by default), plus one to write the answer. Every new or changed chunk, and every question, is one embedding input. The readiness check sends a request of a few tokens on an interval, and each is billed. The admin UI shows the tokens and cost of every conversation.
 How do I size it? Postgres holds one row per item and one chunk row for about every 1,000 characters of text. Qdrant holds one point per chunk, with the quantized vectors and the search graph in memory. The server's memory depends on load more than on the corpus: concurrent Ask turns, PDF extraction, image captions and pushed sessions. See Sizing
.
 How do I back it up? Back up Postgres, the key that seals pasted secrets, and the attachments bucket if you use one. Qdrant needs no backup, because it is rebuilt from Postgres, but the rebuild embeds the whole corpus again. See Backup and restore
.
 Can I change the prompts? Yes, in the admin UI. All model instructions are one catalog. Changes collect in one draft shared by administrators and go live together as one new version with a note, and any earlier version can be made live again. When a new Diderot release ships different prompt text, a "Shipped text" tab lists what differs and you tick what to take. A conversation keeps the version it started with. Tool descriptions are the exception: they live beside the tools, in the code. See Prompts
.
 How stable is it? Diderot is under active development and compatibility across versions is not guaranteed: the MCP tools, the HTTP API, schemas and settings change together. Breaking changes are called out in the release notes and in Upgrading
. Database migrations run when the server starts and cannot be undone: to go back across a release that has one, restore the backup you took before upgrading.
